Why convert an MDB database to SQLite?

SQLite is the most widely deployed database engine in the world — it runs inside phones, browsers, operating systems and countless applications — and a SQLite database is just one portable file. That reach is what makes it the standard landing place for data leaving a legacy Access system: practically every platform and programming language already speaks it, so nothing has to be installed on the receiving end.

An MDB file asks for more (the MDB format guide covers what sits inside one): wherever its data ends up, a Jet- or Access-flavored engine has to come along. Moving Access to SQLite breaks that dependency — the tables arrive in a shape that Python scripts, Android and iOS apps, desktop database browsers and web backends all open directly, with no Access installation anywhere in the picture.

It is also a phone-sized job. Database Viewer turns the device in your pocket into an MDB to SQLite converter that works entirely on-device: open the database, start the conversion, and collect one .sqlite file when the progress finishes.

What carries over into SQLite

The conversion is table-shaped and stays close to what the source actually contains, so it is worth seeing which parts make the trip:

What lands in the .sqlite file

One SQLite table per Access table, keeping the original table and column names and the column order, with every data row coming across. Each column receives a SQLite type — INTEGER, REAL or TEXT — inferred from the data it holds. Binary cells such as OLE objects and attachments travel as BLOB bytes, empty cells arrive as NULL, and boolean-style values are stored as 1 and 0.

What stays behind

Access-only machinery has nowhere to land in SQLite and is not carried: the saved queries, the declared relationships between tables, forms and printed reports. The converter also copies real tables rather than saved views, and it does not rebuild indexes or key rules — the output is a clean container of tables and rows.

In exchange, what arrives is something every SQLite tool understands immediately — no importer, no mapping step, no Access runtime required on the receiving side.

Your original MDB stays untouched

Converting only reads. The app handles your database through a private working copy it never writes to; the converter reads through that copy alone, and every byte of output lands in the new .sqlite file. The MDB you began with ends the job byte-for-byte identical.

Using the SQLite file afterwards

The finished file behaves like any other SQLite database. Open it with the sqlite3 command line, point the SQLite driver of practically any language at it, drop it into an app's assets, or browse it in a desktop database tool — all of these read the converted tables without an import step.

You can also bring it straight back to where it was made: Database Viewer opens SQLite natively, so the SQLite viewer guide doubles as the manual for browsing and querying the file you just produced — on the same phone, with nothing more to install.

Frequently asked questions

Can I convert MDB to SQLite without Microsoft Access?

Yes: the app includes its own native engine and decodes MDB and ACCDB on the phone itself, so Access, Windows and online converter sites play no part in the job. You open the database, run the conversion and save the resulting .sqlite — all inside one app.

Where does the converted file go?

Wherever you point it. When the conversion finishes, the system save dialog opens and you choose a destination — a folder on the device or a location in your cloud drive. The result is a single file named after the original database, ending in .sqlite.

Will conversion change my original MDB?

Never. The converter reads and never writes: it works from the private copy Database Viewer keeps for itself, and everything it creates is the new .sqlite file. Your original database ends the job byte-for-byte intact, and a cancelled run leaves behind no half-written output.

Is converting free?

Looking through the file costs nothing — the free tier exists so you can confirm what the database holds before deciding anything. The conversion itself is a Pro feature, and Pro is a one-time purchase.

Is my data uploaded anywhere?

No. The conversion is computed entirely on the phone: the engine reads the MDB locally and writes the SQLite file locally, with no server, no account and no upload anywhere in the path. The finished file travels only if you later choose to send it somewhere yourself.

What if my MDB file is damaged?

The damage is surfaced first. Before any table opens, the health check reports whether the file reads cleanly, which encoding the file is written in and where damaged regions sit; it also proposes what to do next. That is a diagnosis rather than a repair promise: conversion proceeds from what the file actually contains, and if it reaches a region it cannot read, the conversion stops with a clear error instead of silently skipping past it.
