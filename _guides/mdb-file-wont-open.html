Common reasons an MDB file won't open

An MDB you can't open usually failed for an ordinary reason, not a mysterious one. Five causes cover most cases, and each leaves a different trace in the file — which is why checking beats guessing (the MDB format explainer describes what a healthy one looks like):

  • The transfer never finished. A download that stopped partway, an email attachment squeezed by a size cap, or a copy cut short between drives leaves the file smaller than the database that produced it — and a Jet file missing its closing pages will not open.
  • The file is not an MDB at all. Extensions get lost and swapped in transit. A renamed backup, an export from unrelated software, or a database re-saved in a newer format can all arrive wearing an .mdb name, and the three letters on their own say nothing about the bytes inside.
  • The engine generation predates the reader. The MDB name spans several Jet generations — Jet 3 belongs to the Access 97 edition and Jet 4 to Access 2000 through 2003, with mid-1990s releases older still. A reader built for one generation may stumble on another.
  • The database sits behind a password. Access can seal a Jet database with a database password. The bytes can be perfectly intact and still unreadable without it; whoever administered the database is the right address for that.
  • The storage underneath developed faults. Aging drives and well-worn USB sticks flip bytes silently, and a database rescued from failing media can carry that damage inside it. The trouble lives in the file itself, not in the app that reads it.

Databases saved in the newer ACCDB format run into the same walls; the MDB vs ACCDB guide compares the two Access generations side by side.

What the report can and cannot tell you

Honesty first, because this is where a lot of pages oversell: a health check describes a file. Description is genuinely useful — it turns a mystery into a named problem — but it has edges, and knowing them saves wasted evenings.

What the report tells you

The file's true type — which Access generation, or a different format altogether. Whether its data reads cleanly from start to finish. The character encoding the text is written in. Where damaged regions sit inside the file. And a suggested next step matched to what was found.

What it does not do

It does not bring records back that the damage took out, and it does not rebuild pages that no longer read. Putting a wounded database right belongs to the system that produced it — a copy of Access that still runs — or to a backup made before the trouble. Reading a file and operating on one are different jobs, and the health check does the first.

That is why the report ends in advice rather than promises. When the diagnosis is an incomplete copy, the way forward is a fresh transfer. When the file reads cleanly but nothing opens it, the suspect is the reader, not the data. When damage is real, the source system and the backups hold the ways forward — and the report says so plainly.

If the file opens but looks wrong

Damaged files sometimes still open: the engine gets through the header, most tables read, and a few come up short or stop partway. The report earns its keep here — it marks where the damage sits, so you know which tables to trust and which to treat with caution.

What the damage removed, browsing cannot bring back; that gap belongs to the source system and to backups.

Frequently asked questions

Why won't my MDB file open?

A short list of usual suspects covers most cases: a transfer that stopped before the file was complete, an extension that does not match the bytes inside, a Jet generation older than the reader supports, a database password nobody remembers, or damage picked up from failing storage. A health check tells them apart — it identifies the file, reports whether its data reads and marks where damage sits.

Can an app repair a corrupted MDB file?

A viewer diagnoses; it does not rebuild. Database Viewer identifies the file, reports how far its data reads cleanly, pinpoints the damaged regions and proposes a next step. Putting damaged pages right depends on the system the database came from — a working copy of Access — or on a backup made before the trouble. The check never writes to the file it examines.

How can I check if my MDB file is corrupted?

Install Database Viewer, open the file, and read the report that appears before any table. It is free, it runs on the device, and it states the file's true type, whether its tables read cleanly, the character encoding in use and the regions where damage sits. Nothing is uploaded while it works, and the file is only read.

Is my file uploaded anywhere?

Never. The health check and everything after it happen on the phone: the file is read where it lies, no server receives a copy, and no account is ever asked for. The original opens read-only and stays untouched.

Does this work for ACCDB files too?

Yes. The same checker runs on ACCDB, the format Access has used since the 2007 edition, and it reads a file's generation the same way either way. An .accdb that will not open receives the identical diagnosis: true type, readable or not, encoding and damaged regions.

What if the file opens but some rows are missing?

That pattern usually points to damage in particular regions rather than a uniformly dead file. The report marks where those regions sit, which tells you which tables to trust; the parts that read cleanly stay browsable on the free tier, and taking the readable tables out to CSV or XLSX is a Pro feature, a single one-time purchase. What the damage took, browsing cannot bring back; the gap belongs to the source system and to backups.
